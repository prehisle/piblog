> 2026-10 更新：原文把「档位思考量」当成最硬的信号。后来的生产数据证明它在实际测试条件下不可靠，已经撤掉。「差异藏在哪」和「自查」两节按现在实际计分的项目重写，另补了一节测试本身的局限。

## 起因

上一篇填完 `claude code` 连自建网关的坑之后，我一直被另一个更根本的问题困扰：

我通过中转（或者自建网关背后接的那家上游）拿到的 `claude-opus`，真的是官方的 opus 吗？

用久了会有种模糊的体感：同一个模型名，有时候聪明、有时候明显变笨，高峰期尤其可疑。但体感不能当证据。中转商在后台把 `opus` 悄悄路由到 `sonnet`、甚至 `haiku`，或者套一层别的后端，你在客户端是看不见的，返回的 `model` 字段照样可以写着你请求的那个名字。

于是我花了段时间做了一套测法，专门回答这个问题。这篇讲思路，不卖东西。哪些地方靠谱、哪些地方不靠谱，包括我自己走过的弯路，都尽量讲清楚。

## 一个反直觉的坑：测一次、看一个分，没用

最容易想到的做法是：写个脚本打一发，测测延迟、看看回答质量，打个分。

这条路基本是死的，原因有两个：

1. 绝对分没有意义。延迟、缓存命中、流式粒度这些信号，全都强依赖你当时的网络、账号、上游策略。同一家中转，早上和晚高峰测，数字能差出一截。拿一个孤立的绝对值去下结论，等于拿体温计量室温。
2. 降级是间歇的。真要换模型，聪明的做法是高峰期才换、或者按比例抽着换。单测一发正好没撞上，就误判成「没问题」。

所以单点测量天生抓不到这件事。靠谱的参照系，是让候选通道和官方基线跑同一组题，量两边的差异，而不是量绝对值。

## 思路：和官方跑同一组题，量差异

拆开说：

- 同一组题。所有被测通道和官方基线收到逐字节相同的题，提前锁定，不让随机性掺进来。
- 同一层抓包。请求都从一个透明代理（我用的是 mitmproxy）穿过去，在传输层记录 token 用量、事件到达时刻、响应里的各种字段，这些是客户端平时看不到的。
- 官方同组同跑。每组测试里，除了候选，还有一路官方（直连官方或已知可信的官方口）同时跑同样的题。
- 官方取几次。比的时候，大多数项目拿同一模型最近几次（最多 3 次）官方测试一起比。官方自己单次也会抖，只拿同组那一次容易冤枉人。延迟这种受时段影响最大的，才优先只和同组那次比。

分数从 100 分起，和官方不一样的地方逐项扣。扣多少按对用户的伤害排：没拿到你要的模型或内容最重，其次是多收钱，再次是体验，协议细节上的差别扣得最少。所以最后的分数说的是「这次和官方差在哪、差多少」，不是一个飘忽的绝对分。

## 差异藏在哪

下面是现在实际计分、扣得最多的几类，说的是 Claude Code 这一侧，括号里是这一项最多扣多少（满分 100）。这里只讲机制，具体到某家某次差在哪，得看逐项证据，不能凭一个总分拍板。

**用量对不上（50）。** 上游说这一步输出了 500 个以上的 token，可实际传过来的内容很少，速度又快得不正常（比官方同一个模型最快的时候还快 1.5 倍以上），这一步就判用量对不上。这类问题直接关系到你付多少钱。只是内容少不算：有的上游把思考内容藏起来不传，token 是真花了，这种情况速度是正常的。

**不同问题，一字不差的回答（50）。** 每一步问的都是不相干的问题，真模型不会对两个不同问题给出一模一样的长回答。出现这种情况，基本是网关拿固定内容冒充了模型的回答。

**身份露馅（自我介绍 20，自报型号 20，身份问答 10）。** 响应里的 `model` 字段很容易被改写成你请求的名字，单看它说明不了什么，更有用的是模型自己报出来的身份。让模型自由介绍自己时，不该冒出 Kiro、Windsurf 这类包装层或客户端的品牌名；它在回答和思考里自报的型号，也应和请求的同族、同大版本；按「厂商 / 品牌 / 型号」三行回答时，也要和官方对得上。

**缓存（几项合计最多 30）。** 缓存命中率、5 分钟和 1 小时两种缓存标记、多轮对话里上下文接不接得上，官方都有稳定的样子。包装层经常把这套弄丢或弄乱。按量计费时，没命中的缓存就是多出来的输入费用。

**第一步的输入量（12）。** 第一步的输入体积应接近官方。明显偏大，可能是中转往系统提示里塞了东西；明显偏小，可能是把它剥掉了。

**思考过程（有没有 15，量 8）。** 官方出现了思考内容、候选一次都没有，扣分（同组的官方这次自己也没思考时不扣）；思考量只在官方自己稳定时才比。

**延迟（15）。** 只在稳定地比官方慢一截时扣，比官方快不扣分。

其余还有几项：第 5 步上报的输出量明显高于官方参照（20，报得少不扣）、自报的知识截止时间（5）、同一次回答里信封标的版本和模型自报的版本打架（3），以及一组协议细节字段（消息编号格式、结束原因等，合计最多 8）。协议字段分低多半说明响应被重新拼装过，不直接说明模型被换。Codex 那一侧另有几项（知识召回、推理强度、假流式），这里不展开。

## 一个我自己踩过的坑：用思考量判档位

原文里，我把「档位思考量」当成最硬的信号。实际跑下来，这一条撤掉了，值得单独说一下。

最初的实验条件很干净：低推理强度、提示里要求别推理、不给工具，出一道数数字的题。结果和直觉相反：opus 几乎不想，十几二十个 token 就答；sonnet 想到九百左右；haiku 反而想得最多，上千。三档分得很开。

问题出在生产环境。有的中转商会拒绝不像真客户端的请求（比如不带工具列表的），为了测得到它们，请求得做得更像真实的 Claude Code。改完之后，官方 opus 自己的表现就不稳了：313 个官方样本里，至少四分之三还是 19 个 token，但有一成超过 680，最多到 2330；诚实的通道里，约四分之一被误判。9 月底，这一项连同那道数数题一起撤掉了。

教训是：一个信号能不能用，要先看官方自己在同样条件下的分布，而不是看几次干净的实验。所以我也不再建议靠「思考量时高时低」去判断档位，官方自己就时高时低。

## 一个必须讲清楚的边界：差异不等于掺假

上面这些差异，任何一条单独出现，都不足以断定「这家一定在掺假」。

上游本身不稳、临时被限流、赶上一次真实的临时降级，都会造成差异。所以我这套东西只给参考分，不给「真假」的定性结论。分数低，可能是真降级，也可能只是上游那阵子抖。样本太少时，结论更不稳。

排名取近 30 天的平均。因为通道这一侧的原因跑失败的测试按 0 分算进去，所以经常出错的通道，分数也会低。

正确的读法是：把总分当成一个「值得注意」的信号，然后点进逐项扣分去看到底差在哪（站上通道页的「扣分明细」、对比页的「本次结果」）。逐项证据比一个孤零零的总分靠谱得多，判断留给你自己。

## 测试本身的局限：中转商可能认得出来

站上的常驻测试，用的是 relay-pulse 监测这条通道时配置的 key，请求从本站的服务器发出。中转商有条件认出这些测试，给它们走一条更好的线路。relay-pulse 的入驻协议把「识别出测试后返回与真实用户不同的响应」明确列为作弊，查实将由平台立即下架并公开通报，但从技术上我没法完全排除。

想减少这种可能，可以在站上的提交页用你自己的 key 提交一次，它会和官方一起测，结果公开。这样避开了监测 key 被认出，不过请求仍然从本站的服务器发出，还是有可能被认出来。

## 你自己怎么快速自查

不装任何东西，手动也能做几件事：

1. 响应里的 `model` 字段只能排除最粗糙的换法，更有用的是直接问它是谁：哪家公司、什么品牌、什么型号。留意有没有冒出 Kiro、Windsurf 这类名字。
2. 对一下用量。一条很短的回答，账单上却记了几百上千个输出 token，而且回得飞快，值得留个心眼。开了思考的话要注意，思考的 token 也算输出，只是不一定传给你。
3. 换几个不相干的问题问，看会不会拿到一字不差的回答。
4. 如果账单显示缓存读写，同一段长对话接着问，缓存读取应该占大头；一直是 0，说明缓存没起作用。
5. 别靠思考量判断档位，原因见上。

想省事，就用上一节说的提交页，拿你自己的 key 跑一次。

## 利益披露

把话说在前头，免得被当成软文：

这套方法我做成了一个在线站 rpdiag（`diag.relaypulse.top`），今年 5 月起公开在跑，公开的对比测试已有近 9000 组。排名用到的每次测试，候选和官方的逐项差别都公开可查。现在除了 Claude Code，也测 Codex。

它靠被测的中转商赞助运营，但赞助不参与评分，也不改排序：榜按综合分排，扣分表和改版规则都在站上的方法论页公开。它是一台测质量差别的仪表，不是返佣导航，也不替你做购买决策：只测和官方像不像，不测价格，不给「该买谁」的结论。

上面那条局限（中转商可能认得出常驻测试）也和这层关系有关，所以单独写了出来。一个检测站最该被审视的就是它自己的立场，你完全可以带着怀疑去看它的方法和数据。

## TL;DR

- 想知道中转是不是真模型，测一次、看一个绝对分没用：降级是间歇的，绝对值又被网络和时段污染。
- 靠谱的做法是候选和官方跑同一组题，量差异而不是量绝对值；官方取最近几次一起比，免得冤枉。
- 现在扣分最重的是上报用量和实际内容对不上、不同问题拿到一样的回答，其次是缓存和身份露馅。
- 思考量不适合用来判档位，官方自己就忽高忽低，这一条我已经撤了。
- 差异不等于掺假，常驻测试也可能被中转商认出来。只给参考分，逐项看证据，结论自己下。
